# Repository operating guide

## Product state

- Architecture is closed: nine supported Army Books, fifteen contracts, zero known deviations.
- Supported public/offline books are Death Guard, Adeptus Mechanicus, Tyranids, T'au Empire, Emperor's Children, Chaos Space Marines, Space Marines, Dark Angels, and Blood Angels.
- Orks is configured only for source freshness. It is held, non-public, non-offline, and not a tenth supported Army Book.
- Accepted source facts flow into canonical records, then the validated effective model, then generated publication/runtime projections.
- Canonical/effective records are factual authority. Generated files and compatibility projections are downstream derivatives.

## Start narrow

- Read this file and the nearest scoped `AGENTS.md` before searching.
- Use `docs/codex/REPO_MAP.md` to locate owners and consumers.
- Start with the named book or subsystem, its config, its direct producer, and its targeted QA.
- Do not inventory all books for a local book task.
- Do not reopen closed architecture without a concrete current reproduction.
- Expand only when an actual dependency or shared implementation requires it.
- A Space Marines semantic change may affect Dark Angels and Blood Angels through inheritance.
- A shared runtime/tool change requires regression checks for its affected consumers.
- Cross-book and release suites belong at stage boundaries, not at the start of a local fix.

## Factual ownership

- Follow `book.config.json` and source manifests to accepted inputs.
- Generated `reader.html`, `index.html`, `scripts/data.js`, `scripts/target-data.js`, `scripts/roster-data.js`, and `mobile/*.html` are never upstream facts.
- Global generated glossary files and `roster-guides/points-data.js` are also downstream outputs.
- Fix generated output through its accepted input or producer, then rebuild it.
- Do not restore title-, text-, slug-, order-, or position-derived authoritative identity.
- Use exact canonical IDs and established scope/parent identity for gameplay joins.
- Prefer semantic set/identity assertions over magic counts or generated byte hashes.
- Keep reproducibility, source confidence, and upstream currentness as separate claims.

## Safety defaults

- Do not push, deploy, tag, stamp cache, or run a live source update unless the task explicitly authorizes it.
- Normal builds and checks must remain network-free.
- Treat capture/import/update tools as explicit source-maintenance operations.
- Do not change gameplay, points, identities, source acceptance, or publication scope during tooling/documentation work.
- Do not edit generated files directly unless the task is explicitly about a generated artifact and its producer contract allows it.
- Preserve a clean working tree and review the complete diff before committing.

## Search discipline

- Prefer `rg` and `rg --files` with the smallest relevant roots.
- Search accepted inputs and producers before generated consumers.
- Normally exclude `node_modules/`, `tmp/`, rendered `books/*/mobile/*.html`, generated `books/*/scripts/data.js`, `target-data.js`, `roster-data.js`, and `glossary/contexts/`.
- Do not exclude `books/*/sources/`, `books/*/content/`, configs, manifests, or producer code.
- Search generated outputs only to trace a named consumer, verify regeneration, or inspect a proven publication defect.

## QA workflow

- Run `npm run qa:help` to list the supported targeted entrypoints.
- Use `npm run qa:<book>` for a local book change.
- Use subsystem commands such as `qa:effects`, `qa:points`, `qa:roster`, or `qa:glossary` for shared contracts.
- Follow `docs/codex/QA_MATRIX.md` when a change crosses ownership boundaries.
- Run `qa:integration` after wiring or shared-runtime changes.
- Run `qa:architecture` only as a regression check for architecture-sensitive changes; do not turn it into a new audit.
- `qa:release` is the explicit expensive release gate. It invokes release-stage coverage and is not local QA.
- `test:full` must not appear in ordinary `qa:*` commands.
- Use focused browser QA only when the affected consumer is browser/runtime behavior.

## Builds and sources

- A normal book check is `node books/shared/tools/build-army-book.mjs books/<book>/book.config.json --check`.
- A normal book build may update declared outputs; inspect `generatedOutputs` in its config first.
- Source checks use `npm run qa:sources`; live capture/update remains separate and explicit.
- Points checks use `npm run qa:points`; glossary checks use `npm run qa:glossary`.
- Publication inventory checks use `npm run qa:publication`.
- Never run a source refresh merely to make a normal build or QA pass.

## Reporting

- Separate proven production bugs, stale QA, and unverified hypotheses.
- State the factual owner, root cause, changed paths, QA run, and semantic deltas.
- Report known unrelated debt separately and leave it unchanged.
- For a new major stage, start a new Codex session with the compact handoff in `docs/codex/WORKFLOW.md`.
